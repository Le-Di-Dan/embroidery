# ADR-DB1-007 — ID Strategy

- Status: Accepted
- Date: 2026-07-15
- Git HEAD: `563d9863c5d9591095038a28887e217058d816e4`
- Decision IDs: DEC-04
- Requirement IDs: REQ-INT-004, REQ-REQ-005, REQ-DVER-006, REQ-GRANT-002
- Invariant IDs: INV-19, INV-30 (fixture determinism side), INV-32
- Gap IDs: —

## Context

`BACKEND_CONVENTIONS §5`: "IDs use stable typed conventions selected by ADR."
IDs must be generatable on any machine without coordination (multi-machine,
offline workers), must not leak business volume where exposed, and
append-only tables (audit, ledger, outbox) will dominate row counts.

## Decision Drivers

- Cross-machine, coordination-free generation (multi-machine principle).
- B-tree index locality: purely random keys (UUIDv4) fragment indexes;
  time-ordered keys append.
- Public exposure: order/request references appear in secure links, admin
  UI, and chat texts; they must not be enumerable *as a security boundary* —
  but authorization, not ID opacity, is the boundary (INV-08).
- Append-only internal tables need cheap, ordered, compact keys.
- Deterministic test fixtures (DB7–DB9).

## Options Considered

| Option | Locality | Coordination-free | Notes |
| --- | --- | --- | --- |
| UUIDv4 | poor (random) | yes | pervasive support; index fragmentation |
| **UUIDv7** | good (time-ordered, RFC 9562) | yes | standard since May 2024; PG stores as native `uuid` (16 bytes) |
| ULID | good | yes | non-RFC ecosystem; Crockford base32 needs custom column handling or conversion |
| bigint identity | best | no (DB-generated, sequential) | leaks volume; requires DB round-trip before ID known |

## Decision

### Category 1 — Business/public identity → **UUIDv7, application-generated**

Applies to business aggregates and entities (candidates: Customer, Product,
SKU, Custom Request, Design Version, Approval Snapshot, Quotation, Order,
Payment, Asset, Production Job — final list per DB2/DB4):

- PK type: PostgreSQL `uuid`, value generated **in the application** (single
  vetted RFC 9562 UUIDv7 library selected at DB6; never `Math.random`
  hand-rolls) so aggregates own their identity before insert and outbox
  events can reference IDs pre-commit.
- Time-ordered layout gives near-append B-tree behavior while remaining
  coordination-free across machines.
- UUIDv7 embeds a timestamp — acceptable: creation time is not a secret for
  these entities; anything secret (tokens) is out of scope of IDs (below).

### Category 2 — Internal append-only records → **`bigint GENERATED ALWAYS AS IDENTITY`**

Applies to high-volume, never-exposed, append-only rows (candidates: Audit
Event, Inventory Ledger Entry, Outbox Event, Payment Callback Event, State
Transition Event):

- Compact 8-byte ordered keys; identity generated by PostgreSQL; sequence
  gaps are acceptable and expected.
- These IDs never appear in URLs, API payloads to customers, or exports.

### Category 3 — Public human-readable codes → **separate `code` column, never the PK**

- Request code, order code, quotation number are business-facing strings in
  a dedicated unique `code` column (ADR-DB1-006), generated by the
  application from a configured format (format + counter semantics are a
  DB3/DB4 business-parameter decision; sequential date-scoped formats are
  acceptable because codes are not an authorization input).
- Codes are display/reference identifiers; every access check uses the grant
  /authorization model, never code secrecy.

### Cross-cutting rules (locked)

1. **No sequential or guessable public identifier is ever a security
   boundary**; secure-link tokens (REQ-GRANT-002) are high-entropy secrets,
   separate from IDs and out of this ADR's scope.
2. **Typed IDs in TypeScript:** branded types per entity (e.g.
   `OrderId`, `DesignVersionId`) defined in `packages/domain-types`;
   raw `string` IDs must not cross module boundaries.
3. **Test fixtures** may use fixed literal UUIDs (deterministic), never
   ad hoc generation inside assertions; DB9 formalizes fixture ID ranges.
4. Mixed use is prohibited: an entity's category (1/2/3) is assigned at
   DB2/DB4 and recorded in the ownership map; no per-table improvisation.
5. `gen_random_uuid()` (v4) is not used for PKs; database-side generation is
   reserved for Category 2 identity columns only.

## Consequences

## Positive Consequences

- Coordination-free IDs on every machine and in the worker; stable insert
  performance; compact hot append-only tables.
- Deterministic fixtures and reproducible docs/tests.

## Negative Consequences

- UUIDv7 library dependency (PG16 has no native v7 generator; core
  `gen_random_uuid()` is v4) — small, isolated to the ID module.
- Two ID shapes in the system — mitigated by branded types making misuse a
  compile error.

## Risks and Mitigations

- **Risk:** clock skew on a machine degrades v7 locality.
  **Mitigation:** locality is an optimization, not a correctness property;
  RFC 9562 monotonicity guidance followed by the chosen library.
- **Risk:** timestamp leakage via v7 considered sensitive for some entity.
  **Mitigation:** DB2/DB3 may assign such an entity a random token *in
  addition to* its ID; the ID model stays unchanged.

## Rejected Alternatives

- **UUIDv4 everywhere:** index fragmentation on every hot table for zero
  benefit over v7.
- **ULID:** equivalent properties to v7 but weaker standardization and
  PG-type friction (no native ulid type).
- **bigint for business entities:** requires insert-first identity, leaks
  volume in any exposed reference, complicates cross-machine fixture
  determinism.
- **DB-generated UUIDs for business entities:** application loses
  pre-insert identity (outbox/domain-event ergonomics), and PG16 lacks
  native v7 anyway.

## Deferred Details

- Concrete library and NestJS wiring → DB6.
- Code formats (order/request/quotation numbering) → DB3/DB4 business
  parameters.
- Per-entity category assignment → DB2 (aggregates) / DB4 (tables).

## Implementation Checkpoint

DB6 (ID module + library), DB4 (per-table types).

## Verification Checkpoint

DB7 (PK/unique constraints), DB9 (fixture determinism).

## Reversal / Migration Cost

High after data exists (PK migration); low before DB6 — locked now to keep
DB2–DB5 designs stable.
