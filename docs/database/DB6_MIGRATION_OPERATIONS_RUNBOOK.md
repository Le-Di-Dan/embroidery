# DB6 Migration Operations Runbook

Operator-focused: how to apply migrations `0000`–`0031` to a real environment. Developer/CI
reproducibility steps live in `DB6_REPRODUCIBILITY_RUNBOOK.md`; do not duplicate — this file
covers rollout ordering, failure handling, and rollback/recovery language.

## 1. Preflight (before running `pnpm db:migrate` anywhere but a disposable DB)

1. Confirm target PostgreSQL is `16.14` (the pinned patch, ADR-DB1-001/DEV-DB6-002) —
   applying these migrations against a different major version is unverified.
2. Confirm `DATABASE_URL` (and the discrete `POSTGRES_*` variables it must agree with)
   points at the intended database/schema — `packages/database/src/config/database-config.ts`
   fails fast on a mismatch, but double-check before running against anything non-disposable.
3. Confirm the migration journal state: `SELECT id, hash, created_at FROM
   drizzle.__drizzle_migrations ORDER BY id DESC LIMIT 5;` — the target should currently be
   at migration id 29 or earlier for a rollout that includes `0030`/`0031` for the first
   time (or already at 31 if this is a no-op verification run).
4. **Backup/recovery ownership**: this repository does not yet implement backup/restore
   tooling (DB10 scope, not started). **Production rollout requires an approved
   backup/recovery procedure to exist and have been exercised before applying any
   migration to a non-disposable database.** DB6 does not fabricate that evidence.
5. Confirm no concurrent incompatible deployment is in flight (see §2 rollout ordering).
6. Confirm the migrating role has `CREATE`/`ALTER`/`REFERENCES` on the target schema —
   ordinary DDL privileges, no superuser requirement in any of the 31 migrations.
7. Confirm maintenance-window expectations for `0031` specifically: it adds 27 ordinary
   `CREATE INDEX` statements (§5, lock notes) — plan for a short write-blocking window per
   affected table, not a long one.
8. Run `node tools/db-migration-checksum-check.mjs` from `packages/database` against the
   exact commit being deployed — confirms no migration file was altered post-freeze before
   it ever touches a real database.

## 2. Release ordering

DB6 has not yet been handed a DB4/DB5-owned deployment-ordering document naming an explicit
migration→API→worker→storefront/admin sequence (no such document exists in
`docs/database/` as of this slice — confirmed by search). Pending that handoff, the only
evidence-backed statement DB6 can make:

- **Migration before application startup.** Every migration in `0000`–`0031` is additive
  DDL (new tables/columns/constraints/indexes/functions/triggers); no application code in
  this repository yet depends on any of it (no NestJS modules exist yet), so there is no
  proven ordering conflict today. This will change once DB7 (repository layer) exists —
  that handoff must re-derive the ordering rule then, not inherit this one blindly.
- **No destructive rollback assumption.** Migrations `0000`–`0031` never drop or rewrite an
  existing object; a forward-only migration model (§4) is the current, tested position.
- Compatibility-matrix ownership (which application version each migration is safe to run
  ahead of) is **not owned by DB6** — it belongs to whichever slice first ships application
  code against this schema (expected DB7 or later). DB6 does not fabricate that proof here.

## 3. Apply

```bash
cd packages/database
pnpm db:migrate       # tsx ./src/cli/migrate.ts — the only sanctioned apply path
```

`src/cli/migrate.ts` already redacts the connection string in its own log line
(`redactUrl`) and reports `[db:migrate] up to date` on success with nothing left to apply.

## 4. Rollback / recovery language (canonical position)

- **Migrations are forward-only.** No `down` migration exists or is generated by this
  toolchain (`drizzle-kit` was never asked to produce one, and none of the 31 files were
  hand-authored with a reverse form). Do not write one under deployment pressure.
- **Application rollback** (redeploying a previous app version) is a separate concern from
  **migration rollback** (undoing DDL) and from **database restore** (recovering from a
  backup). This runbook only speaks to the second — the first is owned by whichever slice
  ships the deployable application; the third is owned by DB10 (backup/retention/recovery,
  not started).
- If a migration must be undone in production, the only supported path today is a
  **forward-fix migration** that reverses the effect (e.g., `DROP INDEX` in a new
  `00XX_*.sql` file) — never a manual `DROP`/`ALTER` typed directly against production, and
  never an edit to `0000`–`0031`.
- No automatic rollback tooling exists or is promised by this repository. Do not represent
  otherwise to an operator.

## 5. Lock and rollout notes

- **`0031` adds 27 ordinary `CREATE INDEX` statements** (not `CONCURRENTLY` — this
  toolchain and its migration framework have no support for concurrent-build migrations
  today, and S25/S27 do not introduce one without an explicit canonical decision to do so).
  Each ordinary `CREATE INDEX` takes a `SHARE` lock on its target table for the duration of
  the build, blocking concurrent writers (not readers) on that table only.
- **`0030` adds 30 triggers** (`BEFORE UPDATE OR DELETE`) — `CREATE TRIGGER` takes a brief
  `ACCESS EXCLUSIVE` lock while attaching, released immediately after; no data rewrite.
- Historical migrations (`0000`–`0029`) may have taken longer locks on their own tables at
  the time they were first applied (e.g., `ADD CONSTRAINT` with a new `FOREIGN KEY` requires
  a table scan to validate existing rows) — on an **empty or near-empty** production
  database (this repository has shipped no application code yet, so there is no production
  data), this is not currently a measurable risk. Re-evaluate once real data volume exists.
- **High-write-table concern (forward-looking, not yet measured):** `outbox_events`,
  `audit_events`, `background_job_attempts`, `idempotency_records`, and the transition
  tables are the append-heavy set flagged throughout DB5/DB6 as write-sensitive. `0031`'s
  indexes on these tables (`IDX-088`, `IDX-090`, `IDX-093`, `IDX-094`, `IDX-097`, `IDX-098`,
  `IDX-131`) are the ones most worth scheduling during a low-traffic window once real
  traffic exists.
- **Monitoring signal / abort criterion:** if a migration's `CREATE INDEX`/`ADD CONSTRAINT`
  statement runs past whatever timeout the deployment tooling allows, abort the deployment,
  do not force it through with a longer timeout blindly, and reproduce the exact statement
  against a disposable clone of production-shaped data before retrying.
- **Measured production lock duration is not claimed anywhere in this document** — DB9
  (measured performance validation, not started) owns that evidence.

## 6. Failure handling

### Migration command fails before commit

- Capture the exact error text and SQLSTATE (`src/cli/migrate.ts` already logs
  `[db:migrate] failed: <message>` with the connection string redacted).
- Do not rerun blindly. Inspect `drizzle.__drizzle_migrations` to see exactly which
  migrations committed before the failure (each `.sql` file's statements are wrapped by
  `drizzle-orm`'s migrator in a single transaction per file — see §7 for the exact
  transactional guarantee this toolchain provides).
- Reproduce the failure against a disposable database first (`DB6_REPRODUCIBILITY_RUNBOOK.md`
  §3), never iterate directly against the affected environment.
- Escalate with the migration file name, the exact SQL statement, and the SQLSTATE — never
  with the raw connection string.

### Migration partially applies

Read directly from `drizzle-orm`'s implementation
(`pg-core/dialect.js`'s `migrate()`), not assumed: **every pending migration file in a
single `pnpm db:migrate` invocation is wrapped in one shared `session.transaction(...)` —
the whole batch is atomic, not each file individually.** Verified experimentally in this
slice: a 3-file batch (`0000`–`0002`, with an intentionally broken statement appended to
`0002` in an isolated scratch copy) left **zero** tables and **zero** journal rows behind
after the failure — including the two files that "succeeded" before the broken statement
ran. There is no partial-application state to reconcile after a failed `pnpm db:migrate`
run against an empty-so-far target: the database is left exactly as it was before that
invocation started. Re-running `pnpm db:migrate` after fixing the offending migration
simply re-attempts the same batch from scratch.

The one caveat: this guarantee applies **within a single invocation**. If a database
already has some migrations applied from a *previous, separate* successful run, and a later
run adds new files, only the files pending as of *that* run are batched together — the
earlier, already-committed run is not retroactively affected by anything in the later one.

### Unique/check/index failure

- No silent data cleanup, ever.
- Identify the offending migration and object from the error's constraint/index name.
- Use a read-only diagnostic query against the target (e.g.,
  `SELECT ... FROM <table> WHERE <offending condition>`) to understand the conflicting rows.
- Any data remediation requires an approved, reviewed plan — this runbook does not
  authorize ad hoc `DELETE`/`UPDATE` against production data.

### Drift detected

- Stop the deployment immediately.
- Do not generate an ad hoc migration against the affected environment.
- Reproduce against a clean disposable environment (`DB6_REPRODUCIBILITY_RUNBOOK.md`) and
  compare the deterministic fingerprint (`node tools/db-fingerprint-gate.mjs`) plus the
  live-catalog checkers to identify the exact drifted object before deciding on a forward
  fix.

## 7. Ownership handoffs this runbook depends on

- **Backup/restore/recovery procedure**: DB10 (not started). Required before any production
  rollout per §1.4.
- **Deployment-ordering/compatibility matrix**: first application-shipping slice (DB7 or
  later). §2 states DB6's current evidence-backed position, not a substitute.
- **Measured lock duration and index-build time under real data volume**: DB9 (not
  started).
- **Application/service/controller code that actually calls this schema**: out of DB6 scope
  entirely; this runbook does not write any.
