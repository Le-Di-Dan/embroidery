## C. Implementation

- **Root/header:** `agreements` is a pure header (identity + type +
  current-version pointer only), mirroring `design_cases`'s pattern exactly.
- **Version:** `agreement_versions` carries the frozen legal text,
  `content_hash` (sha256 format, required once non-DRAFT), `effective_from`
  (required once non-DRAFT), and terminal-state evidence timestamps.
  `EFFECTIVE` is derived (not stored), resolved by IDX-108 inside the
  future approval transaction (GRD-008 direction) — never a stored column.
- **Current pointer (`agreements.current_version_id`):** existence FK
  added by hand-authored migration `0019_add_agreement_current_version_fk.sql`
  (same header↔child-cycle mechanism as `0016`/REL-044) — declaring it in
  `agreements.ts` directly would require a circular module import with
  `agreement-versions.ts`.
- **Associations:** `gallery_entry_assets` is genuinely mutable per DB4's
  table catalog (unlike `design_version_assets`'s frozen-with-version
  pattern) — curators may re-order/swap images at any time, so it carries
  `updated_at`.
- **Migration:** two files, both forward-only, no edits to `0000`–`0016`:
  - `0018_create_content_gallery_agreement_tables.sql` — the 6 base tables,
    generated by drizzle-kit from the schema.
  - `0019_add_agreement_current_version_fk.sql` — hand-authored, the
    deferred REL-098 FK, documented inline with the same rationale as
    `0016`.
- **No custom SQL beyond the one deferred-FK statement.** No repository/
  service/controller code. No Quotation/Order/Payment/Reservation field.
