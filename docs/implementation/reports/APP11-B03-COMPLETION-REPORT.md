## E. Public visibility semantics

```text
PUBLISHED only                          = PROVED
noindex still public                    = PROVED
DRAFT indistinguishable from absent     = PROVED
ARCHIVED indistinguishable from absent  = PROVED
unpublish takes effect on next read     = PROVED
```

`PUBLIC_GALLERY_ENTRY_VISIBLE_STATE` is **re-exported** from
`admin-gallery-entry.policy.ts`, so the state B02 publishes into and the state
that makes an entry publicly readable are one literal, not two copies.
`status = 'PUBLISHED'` is a term of every one of the three statements; no code
path fetches a draft for an application layer to filter out.

`isIndexable` is never a predicate. The contract suite proves that structurally,
not in prose: `galleryEntries.isIndexable` appears in the repository's *select*
and never inside an `eq(...)`. The integration suite proves it end to end — a
`noindex` published entry is listed, resolves by slug and streams its bytes.

DRAFT, ARCHIVED and an unknown slug produce byte-identical 404 envelopes; the
suite asserts `code` and `message` equality between the draft answer and the
unknown answer rather than merely asserting both are 404.

## F. Feed semantics

```text
keyset pagination, opaque cursor        = PROVED
display_order ASC, id ASC               = PROVED
image-led safe cover                    = PROVED
zero-deliverable-media entries omitted  = PROVED
no status / search / taxonomy filter    = PROVED
no N+1                                  = PROVED
```

Ordering is `(display_order, id)` — the tuple IDX-066 is built on, with the
unique tie-breaker ADR-DB5-001 R2 requires. The cursor uses the canonical
`@embroidery/persistence` codec **unchanged**: unlike `public-product-cursor.ts`
it binds no filter, because the feed takes none, and a filter term could only
ever hold one value.

The cover, the image count and the "is this entry showable" term are three
correlated subqueries over one shared source fragment, evaluated inside the
single list statement — a page of twenty entries is one round trip. All three
are keyed on the **list** rendition, so "this entry has a cover", "this is the
cover" and "this many images" are one consistent answer.

The omission of an entry with no currently deliverable image is a SQL `exists`
term, not an application filter: filtering after the fact would silently shrink
the requested page and break keyset continuation. The integration suite proves
the omission **and** that nothing was mutated to achieve it — after the only
image is tombstoned the entry leaves the feed while its row still reads
`PUBLISHED` and its one stored association is still there.

The linked product is deliberately absent from the feed: resolving one per card
is the N+1 §12 forbids, and no approved feed card shows it.

## G. Detail semantics

```text
safe ordered assets                       = PROVED
positions renumbered over what is shown   = PROVED
SEO data exposed safely                   = PROVED
zero-deliverable-media -> 404             = PROVED
linked-product public projection safety   = PROVED
no altText field                          = PROVED
```

Assets are returned in the curator's stored `(display_order, id)` order,
restricted to those whose **detail** rendition would really stream — the same
predicate the binary route applies, so the detail can never advertise an address
the media endpoint would refuse. The integration suite proves the equivalence
directly: after filtering, every advertised URL is fetched and returns 200.

`position` is the index in the returned array, not the persisted
`display_order`: publishing a gap would tell a caller that something it may not
see used to sit there.

A published entry with zero deliverable images answers the canonical public 404
— decided in the query, where "an image-led page with no image" is one rule,
rather than inside SQL where it would have taught the repository to distinguish
four cases it must not report separately. Nothing is unpublished and no stored
selection is edited; the operator repairs the media or unpublishes, and the read
reflects it on the next request.

SEO is `{ title?, description?, isIndexable }`, exactly the columns that exist.
No canonical URL, no robots directive, no JSON-LD: those are S03/S04 and B04.

## H. Public media delivery

```text
published gallery required           = PROVED
association to THIS entry required   = PROVED
current public eligibility rechecked = PROVED
canonical rendition resolver reused  = PROVED
safe not-found collapse              = PROVED
canonical binary headers             = PROVED
no storage fact exposed              = PROVED
```

One statement resolves the entire decision — entry publication, the association,
the asset lane, and the derivative's readiness — so there is no window between
"is this entry public" and "which object do I open" in which a concurrent
unpublish could slip through. No object-storage call happens until that query
has succeeded, so a caller probing ids never reaches the provider and cannot use
timing or provider load as an oracle.

**Renditions are reused, not invented.** `PUBLIC_GALLERY_MEDIA_RENDITIONS` *is*
`PUBLIC_PRODUCT_MEDIA_RENDITIONS` (identity, asserted with `toBe`), and
`resolveDerivativeKind` is the catalog's own: `thumbnail → THUMBNAIL`,
`catalog-preview → CATALOG_PREVIEW`. No original, `NORMALIZED`, `MOCKUP` or
`PREVIEW_WATERMARKED` is addressable.

Transport constants are re-exported from `APP2-T01`: `image/webp`, `no-store`,
`inline` with no filename, `X-Content-Type-Options: nosniff`, the `DERIVATIVES`
bucket, `StreamableFile` with client-disconnect teardown. There is no second
MinIO client path and no signed URL anywhere in a JSON body.

### `DELETION_PENDING` — final disposition (closes `FU-APP11-B02-01`)

```text
DELETION_PENDING = REFUSED (not publicly deliverable)
```

Decided from the repository's own authority, not invented for Gallery:

- `APP2-T01`'s public catalog-media repository serves only `assets.status =
  ACCEPTED`, so `DELETION_PENDING` is already undeliverable on the one delivered
  public binary route;
- `payment/domain/evidence/evidence-delivery.policy.ts` calls
  `DELETION_PENDING` and `DELETED` "tombstones";
- both delivered public status projections
  (`order/application/intake/request-asset-status.service.ts`,
  `payment/application/evidence/transfer-evidence.view.ts`) map
  `DELETION_PENDING` onto `REJECTED` and state it is "deliberately absent from
  the public vocabulary".

The predicate is expressed as an exclusion set —
`REJECTED · DELETION_PENDING · DELETED`, plus `deleted_at is null` — rather than
as `= ACCEPTED`. That is the one place Gallery deviates from the catalog
predicate, and it is forced: the asset-inspection worker matches on the
`(kind, classification)` pair and owns only `CATALOG_MEDIA/PRODUCTION_SENSITIVE`
and `CUSTOMER_UPLOAD/CUSTOMER_PRIVATE`, so a `GALLERY_MEDIA`/`PUBLIC` asset
never leaves `UPLOADED` through any delivered pipeline. Copying `= ACCEPTED`
would not have been stricter — it would have made the whole route undeliverable
by construction, which is precisely the mutually-exclusive-lane mistake B02 was
told not to repeat. **Every state the catalog refuses that Gallery can actually
reach is refused here**, and `classification = PUBLIC`, the unwatermarked READY
derivative and the non-null storage key are all applied unchanged.

The integration suite proves each of `REJECTED`, `DELETION_PENDING` and
`DELETED` flips a 200 into a 404 on the same address, and that the asset
simultaneously vanishes from the detail projection.

## I. Repository / application delta

Two new ports, both narrow and both read-only:

```text
PUBLIC_GALLERY_ENTRY_REPOSITORY   listPublished(...) · findPublishedBySlug(...)
PUBLIC_GALLERY_MEDIA_REPOSITORY   findDeliverable(...)
```

Neither takes a lock. `.for('update')`, `.for('share')`, the B02 publication
port, the B01 authoring port, `changeStatus`, `attachAsset`,
`replaceAssetLinks` and `TransactionManager` are all **structurally absent** from
the public read path, asserted by the contract suite over comment-stripped
source so prose cannot satisfy it. A public GET therefore cannot lock a row an
operator is writing, and cannot mutate anything.

No Drizzle row crosses above persistence: the ports return declared interfaces
and the projection maps them to the wire.

### Catalog seam

The linked-product question goes to the **existing** Catalog public read port,
which gains one method:

```text
PublicProductRepository.findPublishedSummaryById(productId)
  -> { slug, name, thumbnailProductMediaId } | undefined
```

By id, because REL-096 stores an id; `undefined` for unknown, DRAFT, ARCHIVED
and withdrawn-category alike, so a caller cannot learn that an unpublished
product exists. It applies the same three visibility terms as the port's other
two reads, from the same constants — Gallery is not a second definition of
product publication visibility and reads no catalog table
(`BACKEND_CONVENTIONS.md` §10). `CatalogPublicModule` now exports the port
symbol; its queries and controllers stay private to that graph.

A linked product that is not public yields `linkedProduct: null` — the same
shape as no link at all — and never affects whether the gallery entry is
visible. Proved both ways, including that the raw `productId` appears nowhere in
the response.

## N. Follow-ups

One blocking phase gap, reclassified by `APP11-B03-C1`, and one non-blocking
item.

- **`FU-APP11-B03-01` — no producer of gallery media exists yet.**
  **Reclassified by `APP11-B03-C1` from `NONBLOCKING` to
  `BLOCKING_PHASE_GAP`, routed to `APP11-B03A`.** This report was wrong to
  file it as a harmless future enhancement: `APP11-B02` may attach only a
  `PUBLIC` asset and `APP11-B03` may deliver only one, so with no delivered
  producer the Gallery cannot be operated end to end at all, and `APP11-A02` is
  a frontend checkpoint that cannot manufacture the missing backend pipeline. The
  audit behind the reclassification, the bounded `APP11-B03A` definition and the
  reconciled HTTP budget are in the APP11 phase document §3.2 and §7.1.
- **`FU-APP11-B03-02` — public gallery responses are `no-store`.** Inherited
  unchanged from `APP2-B04`/`APP2-T01`: there is no cache-invalidation consumer
  in this repository, so any stored copy could outlive an unpublish. Immutable
  public caching and CDN revalidation stay a deployment decision behind a
  dispatcher that does not exist yet.
- **`FU-APP11-B02-01` — RESOLVED by this checkpoint.** See §H.
