### 3.1 Generation note — a drizzle-kit defect that recurs

The file was generated by `drizzle-kit generate`, then hand-trimmed. The
generator emitted two statements beyond the contract: a `DROP CONSTRAINT` and a
re-`ADD` of `ck_approval_snapshots__preview_hash_format`, a constraint this
checkpoint does not touch. The re-add was also **truncated** — it ended at
`'^sha256:[0-9a-f]{64}` with the closing `$'` and both parentheses gone, so it
would not have parsed.

The cause is that the constraint's value contains `$'`, and while the statement
is assembled the value reaches the *replacement* argument of a
`String.prototype.replace` call, where `$'` is the substitution pattern meaning
"the text after the match". The same corruption was written into
`meta/0036_snapshot.json`.

Both statements were removed from the SQL, and the corrupted value in the
snapshot was repaired to the value `0035_snapshot.json` records — which is the
constraint actually installed, since nothing altered it.

**The repair does not stop the defect recurring, and this was verified rather
than assumed.** After the repair, a fresh `drizzle-kit generate` was run purely
as a round-trip check that the hand-edited snapshot matches the schema. It
produced a migration containing *only* that same spurious pair — proof of two
things at once: every other hand-edit round-trips exactly, and the corruption
happens while drizzle-kit reads the schema, not while it writes the snapshot.
A truthful snapshot therefore differs from drizzle-kit's own computation
forever. That throwaway migration was deleted and the journal restored.

The alternative — storing drizzle-kit's corrupted value so future generations
come out clean — was rejected: a snapshot that misdescribes an installed
constraint is a worse failure than a spurious diff a reviewer can see at a
glance. **The next database-change checkpoint should expect the same pair and
trim it the same way.** `app6-cop-design-context-upgrade.integration.spec.ts`
asserts the constraint survives 0036 with its `$` anchor intact, so the trimming
is checked rather than trusted.

The last row is not a rule invented here — it is ADR-APP6-001 §4.1's Catalog

Each branch CHECK is written as **two complete conjunctions** rather than a

as much the failure this guards against as a mixed row is: half a placement is
not a stricter record, it is an unanswerable one.

## 6. FK behaviour, freeze and immutability

### 6.1 `customer_owned_product_id` foreign keys

Both are `ON DELETE RESTRICT` onto `customer_owned_products(id)` —
`confdeltype = 'r'` asserted live — matching every other edge on both tables and
`order_items`' own COP edge (CST-067). `cascade` would delete approval evidence
along with the item it describes; `set null` would leave a row satisfying
neither branch. Deleting a COP that a design version points at raises `23503`,
and an unknown `customer_owned_product_id` is rejected with the same code.

### 6.2 Design-version freeze for the new columns — no trigger change

`0030_add_integrity_triggers.sql` installed CST-090 as
`fn_reject_mutation_conditional('frozen_when_not', 'status', 'DRAFT', 'reject',
'status', 'sent_at', 'approved_at', 'superseded_at', 'voided_at',
'void_reason')`.

That guard is an **exception list, not an allow list**. It diffs every key of
`to_jsonb(OLD)` against `to_jsonb(NEW)` and rejects any change outside the six
named columns, so all three new columns are frozen at the same `TR-LC08-02` send
point as the placement they belong to, from the moment they exist. Extending the
trigger's argument list would have *narrowed* the freeze, not widened it — the
exact inversion the task's §11 warns about.

Proved, not read: a `placement_side_label` edit succeeds while the version is
`DRAFT`, and each of `placement_side_label`, `placement_area_label` and
`customer_owned_product_id` is rejected with `23000` once the version reaches
`SENT_FOR_REVIEW`.

### 6.3 Approval snapshot immutability

`approval_snapshots` carries the row-wide CST-091 guard —
`fn_reject_mutation_conditional('always', '', '', 'reject')` with an **empty**
exception list — so it is column-blind and `customer_owned_product_id` inherits
identical semantics with no change. Duplicating a column-scoped trigger beside a
row-wide one could only weaken it. An `UPDATE` of the new column and a `DELETE`
of the row are both rejected with `23000`.

## 10. What the focused suites caught

The first execution of the branch suite failed 5 of 33. Three distinct defects,
all real, none cosmetic.

### 10.1 CST-130 accepted the rows it existed to reject — three-valued logic

The load-bearing find. The constraint was first written as:

```sql
(cop_id IS NULL AND side IS NULL AND area IS NULL)
OR (cop_id IS NOT NULL AND btrim(side, …) <> '' AND btrim(area, …) <> '')
```

For a COP row with a missing label, the first disjunct is `false` and the second
is `true AND NULL AND …` = `NULL`, so the whole expression is `NULL` — and **a
CHECK constraint passes on NULL**. A COP design version with no side label, no
area label, or neither was silently accepted: precisely the row ADR-APP6-001 §3.7
adds these columns to make impossible.

The blank/tab-only/newline-only cases passed from the start, because `btrim`
returns a real string there. Only the NULL cases slipped through, which is why a
truth table that tests "absent" separately from "blank" was worth writing.

Fixed by making the branch explicit before trimming:

```sql
OR (cop_id IS NOT NULL AND side IS NOT NULL AND area IS NOT NULL
    AND btrim(side, …) <> '' AND btrim(area, …) <> '')
```

`AND` yields `false` as soon as one operand is `false`, regardless of NULLs, so
the row is now rejected. CST-129 and CST-131 were re-examined and are safe: they
are built entirely from `IS NULL` / `IS NOT NULL`, which never evaluate to NULL.
The schema comment records the reasoning so the two `IS NOT NULL` tests are not
later "simplified" away as redundant.

### 10.2 A test fixture collided on `uq_custom_requests__code`

Request codes were built as `REQ-${newId().slice(0, 12)}`. `newId()` is UUIDv7,
whose leading hex **is a millisecond timestamp**, so two requests created in the
same tick share the prefix. The suite now uses the whole id. A fixture bug, but
one that would have made the suite intermittently red for a reason unrelated to
the schema.

### 10.3 The index assertion assumed the Drizzle file was the whole surface

The "no index was added" test enumerated only the indexes declared in the two
tables' Drizzle files, and missed `ix_approval_snapshots__request` (IDX-136),
created by `0031_add_remaining_launch_indexes.sql` outside the table DSL. The
assertion — in both the branch and the upgrade suite — now names the real
surface, so it still fails if 0036 ever adds one.
