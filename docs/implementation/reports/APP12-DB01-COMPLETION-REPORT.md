## E. Orders — origin and custom-chain changes

`orders.origin`, `text`, closed set `CUSTOM | READY_MADE`, final `NOT NULL`,
**no column default at any point**:

```sql
ADD COLUMN "origin" text;                  -- nullable
UPDATE "orders" SET "origin" = 'CUSTOM';   -- backfill
ALTER COLUMN "origin" SET NOT NULL;        -- enforce
```

A default was never added, so it never had to be dropped and no future insert
can be silently classified. `ck_orders__origin_allowed` closes the value set.

The three custom-chain columns dropped `NOT NULL` and immediately regained it
conditionally:

```text
ck_orders__custom_chain_by_origin
  origin = 'CUSTOM'     → all three NOT NULL
  origin = 'READY_MADE' → all three NULL
```

`uq_orders__request` (CST-030) is **unchanged**. PostgreSQL treats NULLs as
distinct in a UNIQUE index, so the one-order-per-request backstop keeps full
strength for custom orders while Ready-Made rows are simply not constrained by
it. Replacing it with a partial index would have changed only its name.

`origin` is immutable after insert (`tg_orders__origin_immutable`). Every rule
in §G is evaluated against it; a mutable discriminator would let a committed row
change what its children were validated against.

## F. Origin/status constraints

`ck_orders__status_allowed` widens from 11 to **13** values. That is the
*column vocabulary*, not a lifecycle — no order may hold all thirteen.
`ck_orders__origin_status_allowed` carries the truth:

| origin | allowed states |
|---|---|
| `CUSTOM` | the LC-14 eleven, unchanged |
| `READY_MADE` | `AWAITING_SHIPPING_FEE`, `AWAITING_PAYMENT`, `READY_FOR_DELIVERY`, `DELIVERED`, `COMPLETED`, `ON_HOLD`, `CANCELLING`, `CANCELLED` |

So a Ready-Made order can never reach `AWAITING_DEPOSIT`, `DEPOSIT_PAID`,
`IN_PRODUCTION`, `PRODUCTION_COMPLETED` or `AWAITING_FINAL_PAYMENT`, and a
custom order can never reach either new state. **No `PAID` state was added** —
settlement is the obligation's fact (LC-15), never a second copy on the order.

`ck_order_transitions__from_status_allowed` and `..._to_status_allowed` widen to
the same thirteen, because a Ready-Made move must be recordable in the table
that records every order move.

## G. Order-item integrity and the cross-table mechanism

`order_items.approval_snapshot_id` became nullable — a Ready-Made SKU line has
no approval snapshot to point at. It did **not** become unconstrained. The
`NOT NULL` it lost was replaced by a cross-table rule, which is what the
invariant always was: `origin` lives on the parent, and no row CHECK can read
it.

**One mechanism, three rules.** `fn_app12_order_origin_guard`, dispatched by
`TG_ARGV[0]`, in the shape `0030`/`0034` established — `SECURITY INVOKER`,
`SET search_path = pg_catalog, public`, `to_jsonb(NEW)` field access so one
function serves triggers on three differently-shaped tables:

| Trigger | Table | Rule |
|---|---|---|
| `tg_orders__origin_immutable` | `orders` | `origin` never changes after insert |
| `tg_order_items__origin_subject` | `order_items` | CUSTOM ⇒ approval snapshot required; READY_MADE ⇒ approval snapshot forbidden **and** `sku_id` required |
| `tg_payment_obligations__origin_kind` | `payment_obligations` | CUSTOM ⇒ `DEPOSIT`/`REMAINING`; READY_MADE ⇒ `FULL` |

The lookup is race-free without a constraint trigger: the child's own foreign
key to `orders` guarantees the parent row is visible to the transaction, and
`origin` can never change, so a value read at INSERT stays true.

**`origin` was deliberately not denormalized** into `order_items` /
`payment_obligations`. A copy would make a plain CHECK sufficient and need no
trigger — at the cost of a second, mutable source for a fact that already has
one. Two copies of a discriminator that disagree is a worse failure than the one
this migration prevents.

The existing `ck_order_items__exactly_one_subject` (CST-067) is untouched, so
with the trigger's `sku_id IS NOT NULL` rule a Ready-Made line can never name a
customer-owned product (§10 satisfied without a second mechanism).

## H. Payment obligation changes

- `kind` gains `FULL`. `DEPOSIT` and `REMAINING` are untouched in name and
  meaning — no rename, no reinterpretation.
- `source_quotation_version_id` becomes nullable, with
  `ck_payment_obligations__source_by_kind` taking the requirement straight back:
  `DEPOSIT`/`REMAINING` **must** name a quotation version, `FULL` **must not**.
  A fabricated derivation is worse than a missing one, so both halves are
  enforced.
- Order-origin compatibility is DB-enforced by the same trigger family
  (§G) — this is *not* left as an application residual.
- `uq_payment_obligations__order_kind__live` is **reused unchanged**. It already
  excludes `SUPERSEDED`, so the pre-payment shipping-fee correction chain
  `PENDING → SUPERSEDED → successor PENDING` works for `FULL` exactly as it
  works for `REMAINING` today. Proved by test, not asserted. **No index was
  added or altered on this table.**

## I. Secure-access changes

- `scope_kind` gains `ORDER_ACCESS` — the second and last scope. No third scope,
  no subject-type discriminator column, no generic polymorphic access platform.
- `custom_request_id` becomes nullable; `order_id` (nullable, FK → `orders`,
  `ON DELETE RESTRICT`) is added.
- `ck_secure_access_grants__scope_subject` makes the pair a **typed XOR**: a
  grant with both subjects, with neither, or with the other scope's subject
  cannot be stored. This is a database invariant, not an application-only one.
- `uq_secure_access_grants__customer_order__active` — the `ORDER_ACCESS` half of
  CST-009. The existing partial unique leads on `custom_request_id`, NULL on
  every order grant, and NULLs never collide; without this a customer could hold
  two ACTIVE grants on one order and a revoke-then-reissue would stop being
  atomic.
- `ix_secure_access_grants__order_id` — the IDX-106 counterpart, for the same
  revoke fan-out and grant-resolution paths.
- `uq_secure_access_grants__token_hash`, the expiry-sweep index and the
  customer index are scope-agnostic already and were not touched. Every
  `REQUEST_ACCESS` guarantee is preserved.
- The `order_id` foreign key is added **by custom SQL in the migration**, not in
  the Drizzle table: `approval_snapshots` imports `secure_access_grants` and
  `orders` imports `approval_snapshots`, so declaring it in the table module
  would close a three-module circular import. Same cycle class as REL-083's
  `satisfied_by_attempt_id`, REL-044/0016 and REL-098/0019.
- `uq_secure_access_grants__customer_order__active` was added to
  `CONSTRAINT_MEANINGS` as `GRANT_ALREADY_ACTIVE`, so a B04 reissue collision
  surfaces as a business conflict rather than an unmapped driver error.

## J. Reservation-expiry persistence

**Schema delta = 0.** `inventory_reservations.expires_at` is already nullable
and `ix_inventory_reservations__expires_id__reserved` already indexes exactly
the rows a sweeper reads (`status = 'RESERVED' AND expires_at IS NOT NULL`), so
an expiring Ready-Made reservation is representable today — proved by the
positive fixture in §M. No redundant table, column or index.

**Documented residual (§19).** An origin-conditional expiry rule was
deliberately *not* added, in either direction:

- `READY_MADE ⇒ expires_at IS NOT NULL` would forbid the legitimate
  post-payment move that clears the window on a reservation which must now
  survive until dispatch.
- `CUSTOM ⇒ expires_at IS NULL` would freeze PO-APP8-002 — a reservation
  *policy* — into DDL that only a migration could change.

Both halves are runtime invariants, assigned to already-locked checkpoints:
**`APP12-B02`** sets the 24h window at Ready-Made order creation;
**`APP12-B04`/`B05`** clear it on FULL satisfaction. This is recorded here and
in the migration header, not left implicit. Existing custom reservations remain
no-expiry and unchanged (§L).
