### Error vocabulary

Six codes added to the one existing translation point
(`domain/admin-gallery-entry.errors.ts`), which now carries ten:

| Code | Status | Meaning |
|---|---|---|
| `GALLERY_ENTRY_VERSION_CONFLICT` | 409 | The stored token does not match `expectedUpdatedAt` |
| `GALLERY_ENTRY_ASSET_DUPLICATE` | 400 | The same image appears twice in one selection |
| `GALLERY_ENTRY_ASSET_NOT_ELIGIBLE` | 400 | The image may not appear in the gallery |
| `GALLERY_ENTRY_PUBLICATION_NOT_READY` | 409 | Requirements unmet; `errors[].code` names which |
| `GALLERY_ENTRY_PUBLISH_NOT_ALLOWED` | 409 | Current state is not `DRAFT` |
| `GALLERY_ENTRY_UNPUBLISH_NOT_ALLOWED` | 409 | Current state is not `PUBLISHED` |

**One code for four different ineligible inputs, deliberately.** An unknown id,
a `CUSTOMER_PRIVATE` asset, a `PRODUCTION_SENSITIVE` asset and a tombstoned one
all answer `GALLERY_ENTRY_ASSET_NOT_ELIGIBLE` with one message. Distinguishing
them is precisely how an endpoint confirms that a customer's private artwork
exists. Proved on the wire: the four cases are a parameterised `it.each` whose
expected body is identical.

Structured detail travels in the platform's canonical `errors` array under
`field: 'requirements'` — the same carrier `productDraftError` uses — never in a
bespoke field this feature invented. No message names a table, a column, a
constraint, a storage key or a classification internal; asserted against
`/gallery_entry_assets|constraint|relation/i` and
`/storageKey|storage_key|bucket|checksum|altText|mimeType/i` on both a success
body and a refusal body.

## E. Ordered asset replacement semantics

```text
replacement, not append     = PROVED
ordered                     = PROVED
cover = first               = PROVED
empty clears                = PROVED
duplicates rejected         = PROVED
PUBLIC-only eligibility     = PROVED
atomic                      = PROVED
concurrency guarded         = PROVED
```

**Replacement, not append.** `replaceAssetLinks` deletes every association for
the entry and re-inserts the supplied ids in one bounded capability — never a
loop of `attachAsset` from the controller, and never a diff. Complete
replacement rather than a diff is the same choice `ProductDraftRepository.replaceMedia`
records, and for the same reason: applying adds and removes leaves a window in
which the stored order is neither the old one nor the new one. Proved by
replacing `[a, b]` with `[c, a]` — an append would leave three associations and
a diff would leave `a` at its old position; the suite asserts exactly
`[{c,0},{a,1}]`.

**Ordered, cover first.** `display_order` is the zero-based request index, so
position 0 is the cover. The write's own response and an independent detail read
are asserted to agree, which is what makes "the list and the detail can never
disagree about which image leads" a property rather than a hope.

**Empty clears.** `assetIds: []` is accepted by the DTO and clears every
association while the entry stays `DRAFT`. It is not an error — it is an
authoring state that only publication readiness later refuses.

**Duplicates rejected, never collapsed.** `new Set(assetIds).size !== length` is
a 400. A curator arranged that list by hand; silently collapsing it would store
an order they did not choose.

**Eligibility.** Every id must satisfy the gallery public-media boundary:
classification `PUBLIC` **and** not tombstoned. Applied as one SQL predicate
(`eligibleAsset`) used by both the selection check and the readiness count, so
"may this image be published" cannot have two answers inside one transaction.

> **Recorded reconciliation — which canonical policy was reused.** §7.3 asked for
> the *existing canonical public-media eligibility policy*. Two candidates exist
> and they are not the same rule. `ProductMediaSelection` (`APP2-B02`) scopes to
> `kind = CATALOG_MEDIA` + `classification = PRODUCTION_SENSITIVE` +
> `status = ACCEPTED`; the delivered AGG-18 `GalleryEntryRepository.attachAsset`
> (DB7-CP3) requires `classification = PUBLIC` and not `DELETED`. **B02 reuses
> the Gallery one**, exactly, for three stated reasons. (1) It is the policy
> already delivered *for this table*, so the batch replacement and the
> single-row attach cannot drift. (2) The product lane's classification is
> `PRODUCTION_SENSITIVE`, which the locked minimum (`PUBLIC`) forbids here — the
> two rules are mutually exclusive, not one stricter than the other. (3)
> Requiring `status = ACCEPTED` would make the endpoint permanently unusable: the
> asset-inspection worker explicitly **refuses** `GALLERY_MEDIA`
> (`apps/worker/src/jobs/asset-inspection/infrastructure/persistence/asset-rows.ts`),
> so a gallery image can never reach `ACCEPTED` through any delivered pipeline.
> No Gallery-specific *parallel* rule was invented, and the boundary was not
> weakened: `CUSTOMER_PRIVATE`, `PRODUCTION_SENSITIVE`, unknown and tombstoned
> are all refused. A stricter treatment of `DELETION_PENDING` is recorded as
> `FU-APP11-B02-01` rather than invented here.

Deliberately **not** scoped to `kind = GALLERY_MEDIA`. The classification
boundary already excludes every private and production lane, and a kind filter
would refuse a customer's own finished work that a publication flow had promoted
to `PUBLIC` — which is exactly the showcase the gallery exists for.

**Atomic.** The order of work is the contract: lock the entry root `FOR UPDATE`,
compare the token, resolve the **whole** selection under `FOR SHARE`, and only
then delete-and-insert. A request naming one bad image therefore changes
nothing. Proved not by absence but positively: the entry under test already
holds a good selection, and after each of the four refusals the suite re-reads
it and asserts both the associations **and** the unchanged `updatedAt`.

**Concurrency guarded.** See §I.

## F. Publication semantics

```text
DRAFT -> PUBLISHED                                   = PROVED
readiness = title + slug + description + eligible asset = PROVED
readiness computed from persisted state              = PROVED
isIndexable=false allowed                            = PROVED
linked product / SEO not required                    = PROVED
guarded concurrency                                  = PROVED
ARCHIVED cannot be published                         = PROVED
```

The closed requirement set lives in `GALLERY_ENTRY_PUBLICATION_REQUIREMENTS` and
is evaluated by a pure function, `evaluateGalleryPublicationReadiness`, over
facts the caller has already read under lock. A refusal returns the unsatisfied
codes in the canonical order, so an operator is told *which* fact is missing.

Absent from the requirement set, each on purpose: `linkedProductId`, `seoTitle`,
`seoDescription`, `isIndexable`, `category`, `style`, `need`, per-image alt text.
`isIndexable = false` is a perfectly publishable entry — asserted by publishing
one.

**Readiness is never trusted from the client.** No readiness field is accepted
on the request, and the evaluation runs inside the publish transaction against
the row locked `FOR UPDATE` and the associations counted through a `FOR SHARE`
join. Two cases prove this is not a formality:

- an image that was eligible when attached and tombstoned afterwards refuses
  publication, and the association is left untouched — readiness refuses, it does
  not repair;
- a stored `title` or `description` blanked directly in the database refuses,
  naming `GALLERY_ENTRY_TITLE_REQUIRED` / `GALLERY_ENTRY_DESCRIPTION_REQUIRED`.
  That state is *unreachable through the DTO*, which trims and requires a title —
  which is exactly why it is the right proof that the check reads persisted state
  rather than the body of the request asking for it.

**`ARCHIVED` is refused by absence, not by a special case.** The publishable set
is `['DRAFT']`; archived is simply not in it, and B02 provides no route that can
reach `ARCHIVED` at all.

No cache invalidation, sitemap job, notification, worker or outbox event was
added. The repository has no already-mandatory lifecycle-event convention for an
equivalent Admin publication that applies to CTX-GAL, so none was invented.

## G. Unpublication semantics

```text
PUBLISHED -> DRAFT      = PROVED
not delete              = PROVED
not archive             = PROVED
assets preserved        = PROVED
SEO/authoring preserved = PROVED
archivedAt untouched    = PROVED
```

`transitionGuarded` writes `status` and `updated_at` and nothing else. One
integration case publishes an entry with two ordered images and both SEO fields,
unpublishes it, and asserts on the response **and** on an independent re-read:
status `DRAFT`; `archivedAt` still absent; `assets` still `[{a,0},{b,1}]`;
`coverAssetId` still `a`; title, slug, description, `seoTitle`,
`seoDescription`, `displayOrder` and `isIndexable` all unchanged; and
`updatedAt` advanced. A second case then publishes the same entry again and
succeeds — so unpublish really left an editable, still-ready draft rather than a
half-dismantled one.

Readiness is deliberately **not** re-run on unpublish: an entry whose only image
was tombstoned after publication is exactly the one an operator most needs to be
able to withdraw.

Structurally asserted, not merely tested: the lifecycle service source, read with
comments stripped, matches neither `/ARCHIVED|archivedAt|archived_at/` nor
`/storageKey|storage_key|signedUrl|publicUrl/`. A transition added later fails by
name.

## H. Repository / application delta

A **second narrow port** was added beside the DB7 authoring contract rather than
widening it — the same shape, and the same reason, as
`ProductPublicationRepository` beside `ProductDraftRepository`: the facts these
three commands need are read and written together, under locks, in one
transaction, and handing every existing `GalleryEntryRepository` consumer a
locking surface it must not use casually is how a plain read starts taking
`FOR UPDATE`. It also keeps both adapter files inside the CLAUDE.md §6 limit.

| Added | Why B02 needs it |
|---|---|
| `GalleryEntryPublicationRepository` (port) | The locking / guarded-write contract for media and lifecycle. |
| `lockAuthoringById` | The entry root `FOR UPDATE`, so two concurrent publications serialise instead of both reading the same stale status. |
| `lockEligibleAssetIds` | The whole selection resolved in **one** statement, `FOR SHARE`, so eligibility still holds at commit. |
| `countEligibleAttachedAssets` | The readiness input, joined from stored associations to locked asset rows. |
| `replaceAssetLinks` | One bounded replacement capability — never a controller-side loop. |
| `touchGuarded` | Advances the token for a media change that alters no column of the entry itself. |
| `transitionGuarded` | Identity + allowed source states + exact token in the one statement that writes. |
| `explainGuardedMiss` | Why a guarded write matched nothing, read inside the same transaction. |
| `gallery-entry-concurrency-token.ts` | `updatedAtMatches` / `nextUpdatedAt` / `publishedUpdatedAt` for `gallery_entries`. |
| `admin-gallery-entry.readiness.ts` | The pure, closed requirement evaluator. |
| `AdminGalleryEntryLifecycleService` | One use case for all three, because all three *are* the same guarded write. |

**One existing seam was touched, behaviour-preservingly.**
`DrizzleGalleryEntryRepository.updateAuthoring` previously stamped
`date_trunc('milliseconds', clock_timestamp())`. It now calls the shared
`nextUpdatedAt()`. This is not a B01 reopening — the contract, the response and
every B01 test are unchanged (22/22 still pass) — it is what makes B02's
concurrency sound: two writes landing inside the same millisecond would
otherwise publish the *same* token, and the second caller's stale value would
still match. A token that can repeat is not a concurrency token. The helper is a
local copy of the accepted Product mechanism rather than an import, because those
helpers name the `products` column in their SQL.

**One service for three operations, not three.** Each command is: lock the root,
compare the token against database truth, decide, write under a guard that
re-tests identity + state + token, project the refreshed detail. Three services
would be three copies of that sequence and three chances for one to drift out of
its transaction. The file is 246 lines.

**Detail representation reused, not forked.** All three operations return B01's
`AdminGalleryEntryDetailResponse` through B01's `toDetailView`. **No B02-only
DTO was created and no field was added to the Admin detail schema.**

## I. Concurrency model

```text
mechanism = body-based `expectedUpdatedAt` (the repository's established
            convention, APP2-B03 / IMP-D035) — no ETag, no header, no second
            protocol
applied to = PUT assets, POST publication, DELETE publication (all three)
```

Mandatory on every command: the DTO has no optional spelling, so a body without
it is a **400**, not an unguarded write. Proved over HTTP.

Two checks, not one. A pre-flight comparison against the locked row gives a
fast, well-classified `GALLERY_ENTRY_VERSION_CONFLICT`; the write itself then
carries identity, allowed source states and the exact token into a single
`UPDATE`, so the state the pre-flight saw is the state the write tests. When the
guarded write matches nothing, `explainGuardedMiss` reads the reason **inside the
same transaction** — a second read outside the guard could observe a different
state than the one the `UPDATE` actually tested, which is the race the guard
exists to close.

Compared at millisecond precision, because that is the precision the token is
published at: `timestamptz` keeps microseconds but a client can only ever echo
back the truncated ISO string it was given.

Each of the three stale-token cases is proved to have written **nothing** — the
suite re-reads the entry and asserts the associations, the status and the
`updatedAt` are all exactly what the concurrent write left.

`APP11-B01`'s `adminGalleryEntry_update` still carries no token; that decision
and its follow-up `FU-APP11-B01-01` are unchanged, and B02 did not reopen it.
